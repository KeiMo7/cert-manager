# 20261120: Rotation-Aware Workload Reload

## Background

cert-manager already renews a `Certificate` and atomically writes the new
bundle into the target `Secret`. The storage side of rotation is solved. The
consumers are not:

- Most workloads read `tls.crt`/`tls.key` once at process start and never
  re-read them. On the expiry day the service stops accepting new TLS
  handshakes even though the `Secret` is already fresh.
- Several workloads can mount the same `Secret`. A notification mechanism that
  reaches only one of them leaves the least-frequently-restarted one holding an
  expired certificate — and that is precisely the pod that fails first.
- Reload mechanics differ: some applications reload on a POSIX signal, some
  expose a local hot-reload HTTP endpoint, some can only be restarted, and some
  operators only want a notification and will handle reload themselves.
- A half-applied bundle (certificate replaced, private key not replaced) makes
  every handshake fail. The old bundle must stay byte-for-byte intact whenever
  a new bundle cannot be produced or validated.

## Goals

1. Reuse the existing issuance pipeline and `Secret` storage unchanged; this
   feature is additive and defaults to the current rotation behaviour.
2. After a `Secret` carrying a certificate changes, notify **every** workload
   that consumes it and drive a configurable reload without restarting the
   cert-manager controller or the workload pod.
3. Never interrupt an established connection. New connections use the new
   certificate while existing connections run to completion.
4. On any rotation failure keep the previous bundle (and every other field of
   the `Secret`) untouched, and raise an alert early enough for a human to
   intervene before expiry.
5. Degrade to periodic file polling when the push notification channel is
   unavailable.
6. Audit every rotation attempt: trigger, target set, per-target result,
   latency and error rate.

## Non-Goals

- Changing how certificates are issued, renewed or stored.
- Requiring any new third-party dependency. All code uses the standard
  library and the Kubernetes libraries already vendored by cert-manager.
- Reaching workloads outside the cluster (the optional
  `rotation-agent` covers nodes/sidecars that cannot receive in-cluster
  notifications).

## Configuration Model

No new CRD is required. Behaviour is declared with annotations on the
certificate `Secret` (which are preserved through cert-manager's Apply because
they live outside the cert-manager field manager's owned fields and can also be
supplied via `spec.secretTemplate.annotations`).

| Annotation | Meaning |
| --- | --- |
| `rotation.cert-manager.io/enabled: "true"` | Opt in. Absent/false keeps today's behaviour: rotate the `Secret`, notify nobody. |
| `rotation.cert-manager.io/target-selector` | Label selector matching consuming pods, e.g. `app in (payments,checkout)`. Required when enabled. |
| `rotation.cert-manager.io/reload-method` | One of `signal`, `http`, `exec`, `none`. `none` means notification only. |
| `rotation.cert-manager.io/reload-signal` | Signal name for `signal`, e.g. `SIGHUP`. |
| `rotation.cert-manager.io/reload-url` | Loopback URL for `http`, e.g. `http://127.0.0.1:9090/-/reload`. |
| `rotation.cert-manager.io/reload-command` | Shell command for `exec` (run inside the target pod via the pods/exec subresource). |
| `rotation.cert-manager.io/reload-window` | Cron-style allowed window (UTC), e.g. `Mon-Fri 01:00-03:00`. Empty means any time. |
| `rotation.cert-manager.io/poll-fallback-interval` | Hint for the degraded polling path, e.g. `60s`. |
| `rotation.cert-manager.io/expiry-warning-period` | How long before expiry a failed rotation must alert, default `168h` (7 days). |

The same `Secret` mounted by ten pods in a namespace is a single
configuration object; the selector fans out to all ten and each target is
tracked independently.

## Components

### Library: `pkg/rotation`

Pure, clock-injectable, transport-agnostic logic, independently unit tested:

- `config.go` — annotation parsing and validation.
- `bundle.go` — `ValidateBundle`: decodes cert/key and requires
  `PublicKeyMatchesCertificate`, so a half-covered bundle is rejected before
  anything is persisted; fingerprinting for retention records.
- `window.go` — reload-window evaluation; a reload whose old certificate is
  inside the warning period overrides the window (safety first) and records an
  event saying so.
- `readiness.go` — pre-rotation checks: opt-in present, selector resolvable,
  reload method configured, command/URL/signal usable, last attempt for each
  target not in a failing state. An unready target blocks rotation for that
  target and raises an event instead of causing an outage.
- `reload.go` — `Reloader` interface plus signal/HTTP/exec/noop executors and
  a graceful certificate store (see below).
- `manager.go` — orchestration: discover targets, check readiness, fan out,
  collect per-target results, retry with backoff, fall back to polling, emit
  audit records and metrics.

### Graceful certificate store

`pkg/rotation/reload.go` provides `CertStore`, an in-process
`tls.Config.GetCertificate` implementation. `Swap` atomically replaces the
presented bundle; the `tls` package calls it per handshake, so:

- new handshakes immediately present the new certificate;
- established connections keep their negotiated state and run until close;
- no listener restart and therefore zero dropped connections.

The `signal` and `http` executors are expected to call an application-provided
hook that performs this swap; the bundled `rotation-agent` does exactly this
and serves as the reference implementation.

### Controller: `pkg/controller/certificaterotation`

Watches certificate `Secrets`. When the `tls.crt` fingerprint changes on an
opted-in `Secret`, it runs the `pkg/rotation` manager against every pod
matched by the selector. State is kept in a status `ConfigMap`
(`cert-manager-rotation-status` in the target namespace): per-target last
fingerprint, last reload result/timestamp and the previous certificate
fingerprint, which is the retention/rollback record.

Registration is behind a new alpha feature gate
`RotationAwareWorkloadReload`, default **off**, so default deployments behave
exactly as before.

### Polling fallback: `cmd/rotation-agent`

A small, standard-library-only agent intended as a sidecar or node helper:

1. periodically stats the mounted certificate files;
2. on content change, validates the bundle (cert/key match, not expired);
3. swaps its `CertStore`, or runs the configured reload command, or raises a
   local signal;
4. exposes `/metrics` (reload attempts, errors, last-success timestamp) and a
   health check that goes unhealthy when the served certificate is within the
   warning period.

It needs no Kubernetes API access and works when the controller's push channel
(exec/HTTP) is unavailable — for example when the Kubernetes API is degraded or
network policy blocks pod-to-pod calls.

## Failure Handling And Retention

- **Issuance failure**: cert-manager never calls the `Secret` Apply, so the
   old bundle and all other `Secret` fields remain untouched. A unit test pins
   this behaviour, and `ValidateBundle` additionally rejects mismatched
   cert/key pairs before any write path can persist them.
- **Notification/reload failure**: the new `Secret` stays (it is valid), the
   target keeps serving the old in-memory certificate until its reload
   succeeds, retries run with backoff, then the polling fallback takes over.
- **Expiry risk**: every reconcile and every agent tick evaluates
   `NotAfter - now` against the warning period; a `RotationExpiryWarning`
   event plus the `certmanager_rotation_expiry_risk` gauge fire while time
   remains for manual intervention.
- **Audit**: each attempt appends an immutable audit record (trigger,
   `Secret` fingerprint, selector, target list, per-target result, latency,
   error) to the status `ConfigMap` and to Kubernetes events; counters and a
   latency histogram are exported as Prometheus metrics.

## Acceptance Criteria

Demonstrated by `pkg/rotation/acceptance_test.go` against a fake workload
fleet (ten pods sharing one `Secret`):

1. One rotation produces end-to-end latency (Secret update → all targets
   serving the new fingerprint) and an interrupt count of zero, measured via
   in-flight connections that continue through the swap.
2. Error rate during the rotation window is zero; a reloader that closes the
   listener is shown to produce a non-zero error rate in a negative test,
   proving the metric catches interrupting reloads.
3. All ten targets receive the notification; missing one fails the test.
4. A failed issuance leaves the original `Secret` (including unrelated fields)
   byte-identical; a half-covered bundle is rejected.
5. With the push transport disabled the polling path converges to the same
   state.

The generated evidence is committed under `docs/rotation/acceptance-record.md`.
